# 製造・テスト工程で判明した知見

仕様は [spec.md](spec.md) にある。ここには**なぜその仕様になったか**、
とくに当初の設計が成立しなかった理由を記録する。

要件定義の時点で決めた手段のうち、実際に動かして初めて否定されたものが多い。
工程ごとに、どの段階でなければ見つけられなかったかを併記する。

| 工程 | 見つかった問題 |
|---|---|
| 製造・単体 | 排他制御が機能しない / 孤児プロセスが残る |
| 実機導入 | iCloud が読めない / 実行コードの置き場所 / Metal が落ちる / モデル参照 |
| 実機テスト（iPhone） | 空ファイルの処理 / リトライの数え方 / バッチ中の検知停止 / 拡張子の前提 |

D 章だけは性質が違う。不具合ではなく、**プロンプトをどう書くべきかをモデルの
挙動から実測した記録**で、道具（`dtp`）の設計根拠になっている。

---

## A. 製造・単体テスト工程

### A-1. 排他制御は `shlock` も `lockf` も使えなかった

当初は `shlock` を採用し、man の「deprecated, use lockf(1)」に従って `lockf` に
変えたが、いずれも成立しなかった。

**`lockf` を親プロセスにする方式**（`exec lockf … "$0"`）は不可。`lockf` は
SIGTERM を子に転送しない。launchd が停止をかけると `lockf` だけが死に、
ワーカーは孤児として走り続け、しかもロックは解放される。そこへ launchd が
再起動をかけると **2本が同時に走り、「直列1本」の保証が壊れる**。実機で再現を確認。

**ファイルディスクリプタで保持する方式**（`exec 9>lock; lockf -t 0 9`）も不可。
ロックの保持と解放そのものは正しく動くが、bash は `exec` で開いた fd を内部で
別番号に複製することがあり `9>&-` では閉じきれない。結果として `sleep` などの
子プロセスがロックを継承したまま孤児化し、最大1秒ロックを握り続ける。
`lsof` で fd 12 として観測した。

**採用した方式**: PID ファイル。`set -o noclobber` による O_EXCL で作成を原子化し、
既存ファイルがあれば「その PID が生きていて、かつ本当に `dtq-worker` か」を
`kill -0` と `ps` で確認する。死んでいれば stale とみなして奪う。`shlock` と同じ
考え方だが PID 再利用まで検証する。ファイルディスクリプタを使わないので、
子プロセスへの継承問題そのものが起きない。

### A-2. 親だけ殺しても作業プロセスは残る

ラッパー経由で起動されたコマンドは、親に SIGTERM を送っても実際に作業している
孫が孤児として残る。GPU を掴んだまま残られると次のジョブと競合する。

子を `set -m` で独立したプロセスグループに置き、`kill -TERM -<pid>` でグループごと
落とす。見張り役は子の生死に加えて**親の生死も見る**。親が SIGKILL で消えたときに
子を道連れにしないと、`draw-things-cli` が最大900秒 GPU を占有し続ける。

## B. 実機導入工程

ここから先は、ターミナルから動かしている限り一つも表面化しない。
launchd に載せて初めて出る。

### B-1. iCloud Drive は「署名済み app バンドル経由」でないと読めない

macOS の TCC により、launchd 配下のプロセスは
`~/Library/Mobile Documents`（iCloud Drive）にアクセスできない。
ターミナルから実行すると読めるので、実機に載せるまで気づけない。

さらに悪いことに、**失敗の仕方が静かだった**。

| 操作 | 結果 |
|---|---|
| `[ -d "$Q_DIR" ]` | **通る**（stat は許可される） |
| `ls "$Q_DIR"` | `Operation not permitted` |
| `for f in "$Q_DIR"/*` | **空**（glob が展開されない） |

「権限がない」と「1件も投入されていない」が区別できず、ワーカーは正常稼働の
見た目のまま永久に何もしない。外出先から投げても静かに無視される、最悪の壊れ方。

**原因**: TCC は身元を特定できないクライアントには確認ダイアログすら出さず、
黙って拒否する。シェルスクリプトを launchd から直接起動すると、プロセスの実体は
`/bin/bash`（Apple の platform binary）であってスクリプト固有の身元を持たない。
利用者に許可を求める術がないまま拒否される。

| 起動対象 | フルディスクアクセス | 確認ダイアログ | iCloud |
|---|---|---|---|
| `dtq-worker`（スクリプト） | 登録済み・有効 | 出ない | 読めない |
| `DrawThingsQueue.app` | 未登録 | 出る → 承認 | **読める** |
| 別ID・別パスの新規署名バンドル | 未登録 | 出る → 承認 | **読める** |

1行目が決め手で、**スクリプトへフルディスクアクセスを与えても一覧に表示される
だけで機能しない**。必要だったのは「許可を手で付与すること」ではなく
「許可を求める窓口が開く形で起動すること」だった。

**対策**:

1. `dtq-setup` が小さな app バンドルをビルドして ad-hoc 署名し、launchd の起動対象に
   する。バンドルの実体はコンパイル済みバイナリ（`launchd/agent/launcher.c`）で、
   `fork` して bash ワーカーを子として動かす。`exec` にしないのは、exec すると
   プロセスの実体が bash に置き換わって TCC 上の身元が失われるため。子は
   responsible process としてバンドルの許可を継承する
2. スイープの先頭で `ls` を試し、失敗したら対処手順ごとログに残す（30分に1回に間引く）
3. `dtq-setup` が起動直後のログを見て検出する。setup 自身はターミナルから動いていて
   権限を持つため同じ `ls` では判定できず、launchd 側のログを見るのが唯一の方法

### B-2. 実行コードを `~/Documents` に置けない

同じく TCC により、launchd 配下のプロセスは `~/Documents` 以下の実行ファイルを
起動できない（`Operation not permitted`、exit 126）。リポジトリを直接指す plist は
動かないため、`dtq-setup` が `~/Library/Application Support/dtq/app/` へ配置し、
plist はそちらを指す。

### B-3. 実行優先度が下がると Metal が落ちる

`ProcessType` を下げると、`draw-things-cli` がモデル読込中に Metal の
`ccv_nnc_mfa_encode_depalettize` で precondition failure を起こし、SIGTRAP で死ぬ
（rc=133）。同一マシン・同一モデル・同一 seed での実測:

| 実行元 | ps 優先度 | 3回中の成功 | 失敗時の所要 |
|---|---|---|---|
| ターミナル | — | 3 | — |
| `ProcessType` = Adaptive | 4 | 0 | 35〜51秒 |
| `ProcessType` 指定なし（Standard） | 20 | 1 | 21〜24秒 |
| `ProcessType` = **Interactive** | 31 | 3 | — |

成功率が優先度と単調に相関する。失敗は必ずモデル読込中に起き、生成まで進めば
必ず完走する。ターミナルからは常に成功するため、launchd に載せるまで露見しない。

`Interactive` は本来「ユーザー体験に不可欠な処理」向けの指定でバッチ生成には
強すぎるが、これより低いと安定しない。GPU を共有している `gRPCServerCLI` との
競合でないことは、両者が動いたままターミナルからは 3/3 成功することで確認した。

当初は `ProcessType = Background` を指定していた。留守中に静かに動く用途には
一見ふさわしいが、**4つの選択肢の中で最も悪い設定だった**。

### B-4. モデルを Draw Things のコンテナから読んではいけない

生成のたびに「ほかのアプリからのデータへのアクセス権を求められています」という
ダイアログが出た。当初これを、出力先が `/Applications/Data/…` にあるせいだと判断し、
**アプリ管理**の権限だと考えて出力先を移した。

**この判断は誤りだった。** システムログで実際の要求内容を確認したところ:

| TCC サービス | 要求数 |
|---|---|
| `kTCCServiceSystemPolicyAppData` | 24 |
| `kTCCServiceSystemPolicyAllFiles` | 8 |
| `kTCCServiceSystemPolicyAppBundles`（アプリ管理） | **0** |

アプリ管理は一度も要求されていない。`/Applications` 配下への書き込みは権限を
必要としていなかった。真の原因は `draw-things-cli` が
`~/Library/Containers/com.liuliu.draw-things/…/Models` を読むことで、これは
Draw Things アプリのコンテナ内データにあたる。

さらに悪いことに、**この許可はエージェントを再起動するたびに失効する**。

| 出来事 | 直後の生成 |
|---|---|
| エージェント起動 | ブロック → 承認 |
| 同一プロセスで継続 | 89〜104秒（正常） |
| エージェント再起動 | **470秒ブロック** → 承認 |
| 同一プロセスで継続 | 89秒（正常） |
| エージェント再起動 | **再びブロック** |

ad-hoc 署名で Team ID を持たない（ログに `Derived team id of (null)`）ことが
関係していると思われる。launchd はクラッシュ時・ログイン時・再起動時に必ず
起動し直すため、**承認を前提にした設計では無人運用が成立しない**。しかも
`draw-things-cli` は承認されるまで死なずに待ち続けるので、留守中は誰も押せず、
タイムアウトまで詰まる。

**対策**: 生成に必要な9ファイルだけを `dtq-setup` がローカルへ複製し、ワーカーは
`--models-dir` でそちらだけを見る。コンテナには一切触れない。複製は
`dtq-setup`（＝ターミナル実行で権限を持つ）でのみ行う。

`cp -c` により APFS のクローンが働くため、論理11GB に対して**実ディスク消費の
増加は 0MB**。ブロックを共有し、どちらかが変更されたときだけ実体が分かれる。

検証: エージェント再起動 → 生成 を2サイクル実施し、いずれも 92秒 / 91秒 で完走、
`AppData` の要求は 0件、ダイアログも出なかった。

なお **ハードリンクは使えない**。`ln` 自体が TCC に引っかかる
（ログに `identifier=com.apple.ln` の AUTHREQ）。`cp` は通る。

### B-5. 許可待ちでブロックされても「成功」に見えてしまう

TCC のダイアログが出ている間、`draw-things-cli` は待たされるだけで死なない。
利用者が承認すればそのまま完走するため、**結果は成功で、ログ上も正常に見える**。
実測では通常88〜104秒の生成が470秒かかった。無人運用ではこの遅延に誰も気づけない。

成功していても所要時間が300秒を超えたら警告として記録し、TCC のログを確認する
手順もログに出す。承認する者がいなければ生成タイムアウト（900秒）で打ち切られ、
リトライを経て failed に落ちるので、静かに詰まることはない。

## C. 実機テスト工程（iPhone からの投入）

**ここまでのテストはすべて Mac 側でファイルを作っていた。iPhone → Mac の実経路は
一度も通っていなかった。** 以下は実機から投入して初めて出た問題で、
自動テストが154件通っていても1件も捕まえられなかった。

### C-1. 同期直後のファイルは `mv` が弾かれる

同期されたファイルは内容が揃っていても、iCloud のファイルプロバイダがまだ掴んで
いて `mv`（ローカルへの取り込み）が弾かれることがある。実測:

```
09:54:01  取り込み失敗
09:55:00  次のスイープで成功（59秒後）
09:55:01  生成開始 → 92秒で完走
```

キューに残して次スイープで再試行する設計がそのまま効き、自己修復した。ただし
当初の実装は `mv` のエラーを `2>/dev/null` で捨てていたため一過性か恒久的かを
判別できず、しかも一過性の状態を ERROR として記録していた。実際のエラー文言を
残し、持ち越し扱いに改めた。

iPhone 由来のファイルには `com.apple.quarantine` が付き、パーミッションは 600 に
なる。読み取り・移動とも問題はない。

### C-2. 未実体化ファイルを空のまま処理していた／リトライを回数で数えていた

iPhone から4ファイルを同時投入したところ、**4件すべてが中身の届く前に failed へ
落ちた**。原因が2つ重なっていた。

**未実体化（dataless）ファイルを検出していなかった。** iCloud の実体が未取得の
ファイルは `.icloud` という名前にはならず、**本来のサイズを報告する**ため
大きさでは判別できない（実測: 実体が無いのに `size=3000724`）。中身が空のまま
ハッシュを取ってしまい、job_id に空ファイルの SHA（`e3b0c442…`）が入り、
`rename` も `Resource deadlock avoided` で弾かれた。

**リトライを回数で数えていた。** `fswatch` は iCloud のダウンロード進行中に何度も
発火する。実測ではスイープが 9〜11秒間隔で回り、**40秒でリトライ上限を
使い切った**。ダウンロードが終わるより先に諦めていた。

**対策**:

- `stat -f '%f'` の `0x40000000`（`SF_DATALESS`）ビットで未実体化を検出し、
  `brctl download` を促して持ち越す
- サイズ0も「まだ届いていない」として持ち越す
- **打ち切りを経過時間で判断する**。同期・移動待ち900秒、JSON の構文エラー180秒。
  スイープが何回走っても結果が変わらない
- 待機ログは30秒に1回へ間引く

### C-3. バッチ処理中はスイープが止まっていた

壊れた JSON の打ち切りが、期限180秒に対して **818秒**かかった。

主ループは `sweep_queue` → `process_pending` の順で回るが、`process_pending` は
溜まったジョブを全部片づけてから戻る。その間スイープは一度も走らない。8件で
13分半、20件溜まっていれば30〜80分キューが放置される。非機能要件の
「検知遅延は最大60秒」を満たせていなかった。外出先から追い足しても、実行中の
バッチが終わるまで反応しないことになる。

ジョブとジョブの間でもスイープするようにした。安定判定の待ちが1件あたり5秒
増えるが、生成が90秒かかることを思えば無視できる。

実機で検証: 30件のバッチ処理中に1件追加したところ、**95秒（生成1周分）で
取り込まれた**。修正前なら45分後まで放置されていた。

### C-4. 形式を拡張子で判断してはいけない

iOS ショートカットの「ファイルを保存」はテキストを **`.txt` として保存する**。
利用者が JSON を書いても `command.txt` という名前で届く。拡張子だけで判断して
いたため、JSON の各行がプロンプトとして扱われ、`"seed": -1,` や `"width": 832,`
といった断片から画像を作り始めた。**無関係な画像を8枚生成し、止めなければ
さらに6枚作るところだった。**

先頭の非空白文字が `{` か `[` なら JSON として扱うようにした。ワーカー側の
同期待ち判定（`jq empty`）も同じ基準に合わせてある。

壊れた JSON が `.txt` で届いた場合は、1行ずつ処理すると事故になるため
`looks_like_json` として止める。

あわせて他ツールの慣習にも合わせた。`seed: -1` は Automatic1111 や
Stability Matrix で「ランダム」を意味するため、未指定と同じ扱いにする。
`count` の上限は 20 から 100 に引き上げた（留守中に何十枚も回すのが本来の用途で、
1枚90秒なので100枚でも約2.5時間）。その後さらに 200 にした → C-5。

### C-5. `count` 上限を 200 にする際に何を確かめたか

上限を決めているのは**時間だけ**で、資源側には余裕があることを実測で確認した。

| 観点 | 実測 | count=200 での見積り |
|---|---|---|
| 時間 | 88秒/枚（34枚連続） | 約4.9時間 |
| ローカル画像 | 1.06MB/枚（911枚の平均、最大2.3MB） | 約210MB |
| iCloud サムネイル | 38KB/枚（686枚の平均、最大105KB） | 約8MB |
| iCloud results | 約4KB/件 | 約0.8MB |
| メモリ | ジョブごとに `draw-things-cli` を起動して終了する | count に依存しない |

メモリが count に依存しないのは、ジョブを**直列に1件ずつ**処理し、1枚ごとに
プロセスが終了するため。同時に走るのは常に1プロセスで、`count` は
`.job.json` の枚数を増やすだけになっている。

`job_id` の連番は `%03d` だが、これは最小桁数であって切り捨てではない。
配列 × `count` で 1000 件を超えても `-1000` と桁が伸びるだけで衝突しない。

**残る制約は時間**。5時間の連続生成中はスリープさせられないうえ、
`RETENTION_DAYS=30` の掃除対象は `thumbs/` と `results/` だけなので、
ローカルの原本は貯まり続ける。

## D. プロンプトの実測（モデルの挙動）

「日本語の自然言語で指示したい」という要望に対し、変換の仕組みを作る前に
**変換が必要かどうかを測った**。結果として当初案（日本語→英語の翻訳層＋語彙辞書）は
不要と分かり、設計が大きく変わった。

測定はすべて同一シード・同一パラメータで、変えたのはプロンプトだけ。
モデルは Z-Image Turbo 系 q8p（テキストエンコーダ Qwen3-VL 4B）、steps 8、LoRA なし。

### D-1. 日本語はそのまま通る。英語より良い場合すらある

同一シーン（赤いマグ／木の机／朝の光／観葉植物「一つ」）を日本語・英語・中国語で
記述し、seed 777001 で比較した。

| 言語 | 数量指定「一つ」 | 「朝の光」の解釈 |
|---|---|---|
| 日本語 | 守った | **机に光条が落ちる** |
| 英語 | 守った | 平坦、方向性なし |
| 中国語 | **無視。複数鉢** | 平坦 |

エンコーダが Alibaba 製なので中国語が最も通ると予想したが、**逆だった**。
中国語だけが数量指定を落とした。

人物シーン（喫茶店・逆光・浅い被写界深度・憂鬱な表情）でも日本語が優位で、
**日本語のほうが文脈が濃い**。日本語だと蝶ネクタイの店員と客のいる「日本の喫茶店」に
なるが、英語だと無国籍なカフェになり背景の情報が失われる。日本語が日本の視覚概念を
引き当てていると考えられる。

### D-2. 再現性はビット一致しない。その差が測定の物差しになる

**同一プロンプト・同一シード・同一パラメータでも、実行ごとに画像は一致しない。**
画素の 85.6% が異なる。ただし平均絶対差は 4.85/255（1.9%）で、**見た目は区別できない**。
GPU の浮動小数点の畳み込み順序が実行ごとに変わるためと考えられる。

実務上は「再現する」と言ってよいが、**ビット一致を前提にした設計はできない**。
リトライで再生成した画像は初回と同一にならない。

より重要なのは、この 4.85 が**ノイズ下限として使える**こと。プロンプトを変えた
ときの差がこれに対して何倍かを見れば、「効いたのか、たまたまか」を主観でなく
数値で判定できる。

### D-3. 何語で書くかより、何を書くか

seed 424242 / 832×1216 で、記述量と言語を変えて平均画素差を測った。

| 変更内容 | 平均差 | ノイズ比 |
|---|---|---|
| 同一プロンプトを再実行 | 4.85 | **1.0（基準）** |
| 写真用語だけ英語に | 23.4 | 4.8× |
| 短→中（服装・雰囲気を追加） | 51.1 | 10.5× |
| 中→長（光・カメラ・媒体を追加） | 57.9 | 11.9× |
| 全文を英語に | 68.8 | 14.2× |

**記述量を増やす効果が、言語を変える効果に匹敵する。** 一方で写真用語だけを
英語にする効果はその半分以下で、しかも検証6項目のいずれでも改善しなかった。
`逆光` は `backlit` と、`中望遠レンズ・浅い被写界深度` は
`85mm medium telephoto lens, shallow depth of field` と同等に機能する。

見た目の変化も一貫している。

- **主題と場所だけ**（1文）: 全身の量産型ストック写真。平坦な照明、被写界深度なし。
  `夕方` すら効かない
- **＋服装・雰囲気**: 構図が寄り、劇的に改善。ただし光は環境光のまま
- **＋光・カメラ・媒体**: 逆光のリムライト、ガラス越しの構図、粒状感が出現

### D-4. 設計への帰結

翻訳層も語彙辞書も作らない。**日本語のまま完結させ、道具は「書き忘れを潰す」ことに
集中する**。必須スロットは D-3 の効果量がそのまま根拠になる。

出力順序は測定で良好だった L のプロンプト構造に合わせる
（場所 → 主題 → 動作 → 服装 → 光 → 雰囲気 → カメラ → 媒体）。

A/B テストの判定には D-2 のノイズ下限 4.85 を使う。語彙が効いたかどうかを
数値で言えるので、**未検証の語彙は利用者自身が測って積み上げられる**。


### D-5. 組み立てた文が元の文構造から劣化しないことを確かめた

`dtp` は1スロット1文で並べるので、実測に使ったプロンプトとは文構造が変わる。

| | |
|---|---|
| 実測した文（L） | 夕方の喫茶店の窓際**に座る**20代の女性。… |
| 組み立てた文 | 夕方の喫茶店の窓際**。**20代の女性**が席に座っている。**… |

内容は同じで、`場所` と `主題` が1文か2文かだけが違う。同一シードで生成して
比較したところ **ノイズ比 4.2倍（平均差 20.55）**。写真用語を英語に替えたとき
（4.8倍）とほぼ同じ大きさで、記述量を変えたとき（10〜12倍）よりずっと小さい。

目視では検証6項目すべてを保持していた（ニット・逆光のリムライト・浅い被写界深度・
喫茶店の店内・憂鬱な表情・フィルム調）。ガラス越しの構図も残った。差は構図が
わずかに引いたことによるもので、劣化ではない。

**組み立ての語順保証は、文の融合まではしなくてよい**と判断した。

なお同じ比較を2つの参照画像（L と、L と同一文の別実行 A）に対して行い、
20.55 と 20.54 になった。測定自体が実行ごとのゆらぎに影響されないことの確認にもなる。

### D-6. カンマ断片か散文かは、ほとんど効かない

`dtp` の lint は当初「カンマ区切りのタグ列に見える。自然な文章のほうが通る」と
警告していた。これは D-3（散文どうしの比較）からの外挿で、**断片形式と散文を
直接比べてはいなかった**。

実運用のアーカイブを見ると、プロンプトは 7〜11 のカンマ断片で書かれている。
つまりこの警告は毎回出ることになる。測って確かめた。

条件は実運用に合わせた（同一シード、LoRA 2種、832×1216、steps 8、
negative は `blurry, distorted, text`）。

| 比較 | 平均差 | ノイズ比 |
|---|---|---|
| 形式だけ変える（同じ情報量の断片 vs 散文） | 12.99 | **2.7倍** |
| 記述量だけ変える（断片どうし、情報量を増やす） | 25.72 | **5.3倍** |
| 両方変える | 25.85 | 5.3倍 |

**記述量が支配的で、形式はほとんど効かない。** 両方変えても記述量だけの差と
同じ値になり、形式は上乗せしていない。目視でも、同じ情報量なら断片形式と散文は
見分けがつかなかった。断片のほうが劣るということもない。

**警告を削除した。** 効くのは形式ではなく記述量であり、それは推奨スロットの
警告が既に担っている。直さなくてよいものを毎回指摘するのは雑音にしかならない。

D-3 の結論（何語で書くかより何を書くか）が、書式についても成り立っていた
ことになる。**書き方の作法ではなく、書いた内容だけが効く。**

なお当初の比較には交絡があった。散文版が形式と記述量の両方で違っていたため、
「同じ情報量の断片」を対照として1本足して切り分けている。

## E. 横断的な教訓

**1. ターミナルで動くことは、launchd で動くことを何も保証しない。**
TCC の身元、実行優先度、権限の永続性 — B 章の問題はすべてこの一点に帰着する。
常駐させる設計なら、早い段階で launchd に載せて確かめるべきだった。

**2. 自分で作ったテストデータは、本物の入力と違う。**
ローカルで作ったファイルは最初から実体があり、同期遅延も、余計な拡張子も、
`com.apple.quarantine` も付かない。C 章の問題は自動テスト154件が1件も
捕まえられなかった。**入力がどう作られるかは、作り手の環境が決める。**

**3. 静かに壊れる実装が一番危険。**
権限がなくて glob が空になる、未実体化ファイルを空として処理する、
許可待ちのブロックが「成功」に見える — いずれも異常が異常として現れなかった。
「何も起きていない」と「起きているはずのことが起きていない」を区別できる形で
書く必要がある。

**4. 回数で数えるリトライは、イベント駆動と相性が悪い。**
リトライ回数はイベントの発生頻度に依存してしまう。待つ理由が時間である以上、
打ち切りも時間で決めるのが正しい。
